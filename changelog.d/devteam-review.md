### Added

- **`devteam review <path>` — the zero-install external-review entry point (phase-36 item 36.4, `plans/phase-36-external-review-mode.md`).** No `init`, no config, nothing written to `<path>`. Creates (or reuses, via `--workspace <path>`) a review workspace under `~/.stagecraft/reviews/<slug>/` (`core/review-workspace.js`, item 36.3), then dispatches `--track` (default `review-only`) through the normal bounded driver (`core/driver.js#run()`) with `ctx.cwd` = the workspace and `ctx.processCwd` = the subject and `ctx.externalReviewMode = true` — the two-root split 36.3 wired through `runStage()`/`runStageHeadless()` but that, until this item, no caller ever set to `true`. `hosts/acp/adapter.js` reads that flag to flip its permission evaluator (`hosts/acp/permissions.js`, item 36.1) into review mode: any write into the subject is denied, and `execute` becomes a read-only allowlist. `--scope <path>` (repeatable) narrows the review the same way `devteam run --scope` already does (35.1). On completion, runs 35.4's severity-ordered findings collector/renderer against the workspace and prints the report path (`--open` launches it in a browser).

  **Host honesty.** `acp` is the only host whose enforcement is mechanical rather than advisory (`hosts/acp/permissions.js`'s two-root evaluator vs. every other host's prompt-only or post-hoc-audit `allowed_writes` — `core/adapters/render-helpers.js#allowedWritesCaption`). `--host` naming anything else prints a one-line warning that writes to the subject are **not** prevented (enforcement degrades to a post-hoc write audit) and refuses to proceed without `--allow-unenforced-writes` — the house "allow-&lt;compromised-guarantee&gt;" convention (`evidence.js`'s `--allow-unverified`), chosen so the flag itself states what's being given up, not just that the user consents. The warning still prints even when the flag is passed; this command never prints a read-only claim a host cannot keep.

  **`devteam review --list`** enumerates `core/review-workspace.js#reviewsRoot()`, pairing each workspace's `subject.json` (what's being reviewed) with a new `last-run.json` (recorded by this item, not 36.3 — run outcomes, not review-target identity) for subject path / last run date / last status. An empty list renders as "no review workspaces yet," not an error.

  **`--json`** is schema-checked against two new checked-in schemas: `core/review/schemas/review.schema.json` (single-run output: subject identity, workspace path, host/track, `review_mode_enforced`, driver completion state, findings-report summary) and `core/review/schemas/review-list.schema.json` (`--list` output).

  **The test that matters** (`tests/review-command.test.js`): end-to-end against a fixture subject repo, driven by a new scripted ACP agent (`tests/fixtures/acp-stub-review-agent.js`) that completes the *entire* three-stage `review-only` track (security-review, red-team, and all four peer-review areas) in one process invocation by parsing each dispatch's own rendered prompt for its workstream id/role, artifact path, and gate path — `tests/fixtures/acp-stub-agent.js`'s fixed-env-var approach only covers one dispatch per process, which a full `devteam review` run can't offer since the CLI's single invocation drives every stage's dispatch with the same env. Asserts the subject tree (file list + content hash, `.gitignore`/`AGENTS.md` included) is byte-identical before and after, a findings report is written, and `--list` picks up the completed run afterward. Also covers: `--list`'s empty case; the non-acp host warn-and-refuse-without-ack / proceed-with-ack paths (no workspace created on refusal); and both `--json` shapes against their schemas.

  Honest scope note: this item does not change how `Produce <artifact>` / `Write to pipeline/gates/<id>.json` are rendered (`core/adapters/render-helpers.js`) — those instructions are still *relative* paths, which a real (non-scripted) ACP agent would resolve against its own session cwd. In review mode that cwd is the subject (36.1's `processCwd`), not the workspace, so a real agent following the prompt literally would either get its write denied (safe: review-mode's codeRoot check catches it) or would need to independently infer the workspace's absolute path from context this prompt doesn't currently give it. 36.2 solved exactly this ambiguity for *read* targets (framework `readFirst` entries render absolute when roots differ); the same fix for *write* targets (artifact + gate paths) is not part of this item — flagged as an out-of-scope finding, not fixed here. The scripted test stub sidesteps it by being told the workspace's absolute path directly via `ACP_STUB_WORKSPACE_ROOT`, the same way `tests/fixtures/acp-stub-agent.js` already sidesteps path ambiguity for 36.3's own test. Also unaddressed here: `hosts/acp/adapter.js` never calls `core/hooks/approval-derivation.js#deriveForProject` the way `core/adapters/headless.js` does for non-ACP headless hosts, so a *real* ACP-routed peer-review dispatch has no automatic path from a `by-<role>.md` review file to a derived `stage-05.<role>.json` gate — this item's test stub writes that gate directly (a scripted stub, not bound by the "never authored by an agent" contract stage-05's schema describes), which is fine for testing this command's orchestration plumbing but does not exercise or fix that gap.
