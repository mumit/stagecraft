### Added

- **Orchestrator-verified evidence for stage-06d (verification-beyond-tests) — Phase 35.3.** `STAMPABLE_STAGES` was `{stage-03b, stage-04a, stage-04c, stage-06}` — stage-06d, the stage whose entire value is verification depth, was 100% model self-report: a gate claiming `methods_attempted: ["property"]` was believed with no orchestrator check. `core/verify/stamp.js#stampStage06d` closes that gap: for every method the model claims with a bare tag (`"property"`, `"mutation"`, `"formal"` — not an already-honest `attempted_but_blocked:*`), the orchestrator tries to produce real executable evidence before the claim is accepted.
  - **Property-based** (`core/verify/property.js`): detects fast-check (JS/TS, package.json dependency), hypothesis (Python, requirements.txt/pyproject.toml), or proptest (Rust, Cargo.toml) — never installs any of them. Runs the property tests found under `pipeline.verify.property.paths` (default `src/tests/property/`) and parses the runner's own summary for an executed-property count and pass/fail. fast-check runs via Node's built-in test runner (`node --test --test-reporter=tap`); a genuine counterexample (`Property failed after N tests`) FAILs the gate on orchestrator evidence, and a claim backed by zero executed properties downgrades to `attempted_but_blocked:property`.
  - **Mutation**: reuses the phase-31.4 runner (`core/verify/mutation.js#runMutationGate`) directly — no second implementation. Honors the model's own pre-declared `threshold` (the schema calls this "audit-grade: prevents goal-post moving"); a re-run score below it FAILs the gate, unlike stage-06's smoke gate where below-threshold is advisory by default.
  - **Formal** (`core/verify/formal.js`): presence-and-exit-code only. TLA+/Alloy/Lean/Coq output is too varied to parse reliably, so the orchestrator stamps `{tool, ran, exit_code}` and nothing more — a non-zero exit raises a warning for human triage, never an automatic FAIL. No manifest auto-detection (no single signal the way fast-check has one); the project declares its check via `pipeline.verify.formal.command`.

  `stage-06d` joins `STAMPABLE_STAGES` (`devteam verify stage-06d` now works) using the existing single-workstream dispatch path in `core/orchestrator.js` — no orchestrator wiring changes were needed there. A method the model never claimed (a legitimate `methods_skipped` entry, or an already-honest `attempted_but_blocked:*`) is left untouched; the orchestrator verifies claims, it doesn't invent new ones. `.devteam/config.yml` gains commented `pipeline.verify.property` / `pipeline.verify.formal` documentation alongside the existing `mutation` block.

  Tests: `tests/verify-stamp-06d.test.js` — a fixture with a real fast-check-shaped counterexample FAILs on orchestrator evidence while the method claim stays confirmed (it did run); a model claiming `property` with zero executed properties downgrades to `attempted_but_blocked:property` with the model's original claim preserved under `_orchestrator_stamped.runs.property.model_claim`; absent toolchain (no fast-check/hypothesis/proptest signal) records the same downgrade; mutation claims below/above the model's declared threshold FAIL/PASS respectively using a `command`-override fixture (mirroring `tests/verify-stamp-mutation.test.js`); formal claims downgrade when unconfigured, stamp `{tool, ran, exit_code}` on exit 0 without touching the model's other formal fields, and warn-without-failing on a non-zero exit; a legitimately skipped method and an already-honest `attempted_but_blocked:*` claim are left untouched; unit tests for `detectRunner`/`parseOutput`/`buildCommand`/`walkFiles` (property.js) and `resolveFormalConfig` (formal.js) against canned tool output. No pre-existing `tests/verification-beyond-tests.test.js` test required changes — that suite covers the model-facing schema/skill/template/prompt surface, which this change doesn't touch.

  Honest scope note: only the fast-check/Node-built-in-test-runner path is integration-tested end-to-end (via a `command`-override fixture, following `tests/verify-stamp-mutation.test.js`'s existing pattern — this repo carries no real fast-check dependency, matching the "never install" doctrine). hypothesis (pytest-style summary) and proptest (`cargo test`-style summary) detection and output-parsing are unit-tested against canned strings only, since this repo has no Python or Rust toolchain to run them against for real. Formal-method exit codes are intentionally never interpreted as pass/fail by the orchestrator — a non-zero exit could mean a genuine counterexample or a tool/config error, and the plan explicitly asks for presence-and-exit-code evidence only; this is a deliberate, narrower guarantee than mutation's, not an oversight.
