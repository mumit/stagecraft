### Added

- **Cache-first prompt assembly — Phase 32.1.** Every `renderStagePrompt` implementation (`core/adapters/markdown-host.js` — shared by codex/gemini-cli/openai-compat/antigravity/omnigent — plus `hosts/claude-code/adapter.js` and `hosts/generic/adapter.js`) now assembles the stage prompt in a fixed four-layer order: (1) framework preamble/rules (`core/pipeline/stages.js`'s new `FRAMEWORK_READ_FIRST` — the constant `AGENTS.md` + rule-file prefix every dispatched stage's `readFirst` already shared), (2) role brief (the role-prompt pointer, or the inlined brief itself for the `generic` adapter), (3) learned context (Known Project Patterns + Prior Project Knowledge, unchanged content, just repositioned), (4) the volatile tail (stage header, objective, the stage-specific `readFirst` remainder, changed-file manifest, allowed writes, gate shape). Layers 1–2 are now byte-identical across every dispatch in a run that shares the same role — the prefix providers/CLIs can cache automatically. Each adapter also exports `renderStagePromptLayers()`, returning the per-layer text alongside the full joined string, for callers that need the layer boundaries (e.g. cache_control placement).

  For `openai-compat` against Anthropic-compatible endpoints, opt in via `hosts.openai-compat.caching.enabled: true` — `invoke()` then sends the prompt as separate content blocks with `cache_control: {type: "ephemeral"}` after layers 1–3 (empty layers, e.g. no learned context yet, are dropped rather than sent as empty blocks; the volatile tail never carries a breakpoint). OpenAI-style endpoints need no config — they get prefix caching for free from the stable ordering alone. `cached_tokens`, when the API reports it under `usage.prompt_tokens_details`, continues to be recorded via the existing phase-28.2 mechanism onto the gate's `_orchestrator_observed` block.

  Tests: `tests/prompt-layout.test.js` — `splitReadFirst`/`renderFrameworkPreamble` unit coverage; a meta-test asserting every dispatched stage's `readFirst` starts with `FRAMEWORK_READ_FIRST`; the prefix-stability regression (two different stages, same run, same role → layers 1–2 byte-identical, layers 3–4 legitimately differ) across every adapter that exposes `renderStagePromptLayers`; `buildCacheAwareContent` fixtures for breakpoint placement and empty-layer dropping; an `invoke()` fixture proving `cache_control` content blocks are only sent when `caching.enabled` is true, plain-string content otherwise. Reordering required no changes to any pre-existing test — the full suite (`npm test`, `CI=true DEVTEAM_HEADLESS_COMMAND=cat npm test`) stayed green throughout, and `docs/reference/prompt-budget.md` regenerated byte-identical (the generator sources stage/role file sizes directly, independent of rendered-prompt section order).

  Honest scope note: `renderStagePromptLayers()`'s layer-3 "learned context" is only *positioned* as constant-per-run — its actual content (`descriptor.knownPatterns` / `descriptor.priorKnowledge`) is still selected per stage/workstream by phases 30/31's existing retrieval logic, so it can legitimately vary dispatch-to-dispatch within a run; only layers 1–2 carry the byte-identical guarantee the regression test checks. Claude Code, Codex, Gemini CLI, Antigravity, and Omnigent get the ordering benefit only (whatever automatic prefix-caching their own CLI/API already does); Stagecraft has no hook into those CLIs' own request construction to add explicit cache breakpoints there. `cache_control` support is opt-in and unverified against a real Anthropic-compatible proxy in this change — the fixture stubs `fetch`, so the request shape is proven, not a live cache hit.
