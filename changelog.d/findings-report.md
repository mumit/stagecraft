### Added

- **Severity-ordered findings report with mitigations — Phase 35.4.** Today, "put an existing codebase through reviews and get one list of things to fix" means hand-assembling it from `pipeline/security-review.md`, `red-team-report.md`, `code-review/by-*.md`, `pipeline/gates/stage-06d.json`, and `docs/audit/*.md` separately. `devteam report --findings [--out <file>] [--json]` collects one ranked table instead: severity, `file:line`, what's wrong, suggested mitigation, rough effort, and provenance.
  - **Sources** (`core/report/collect-findings.js`): security-review (stage-04b `BLOCKER:` lines, escalated to `critical` on veto), red-team including the 31.2 mechanical floor (stage-04c `must_address_before_peer_review[]` / `noted_for_followup[]`, cross-enriched with `red-team-report.md` prose for mitigation/effort/file:line), peer-review + critic (stage-05 blockers, stage-05.critic.json unresolved challenges), the 31.4 mutation smoke gate (stage-06), verification-beyond-tests (stage-06d `blocking_findings[]` / `non_blocking_findings[]`), and `docs/audit/*.md` once `docs/audit/status.json` shows the audit workflow has run.
  - **Provenance is the important column**, reusing the existing `_orchestrator_stamped`/`_orchestrator_observed` distinction rather than inventing a new one: a finding is `orchestrator-observed` only when it traces to code the orchestrator itself ran — a mechanical red-team floor check (`source: "mechanical"`), an executed mutation gate, a stage-06d method the orchestrator actually confirmed with real evidence (not downgraded to `attempted_but_blocked:*`), or a peer-review approval mismatch the approval-derivation hook derived from the review file. Everything else — a reviewer's or auditor's judgment, even when well-evidenced in prose — is `model-asserted`.
  - A generic markdown finding-block parser (`core/report/parse-markdown-findings.js`) reads the "heading + bullet fields" shape shared, with drift, by `red-team-report.md` (`### RT-1 — <title>`) and `docs/audit/*.md` (`#### Finding S1: <title>`) — used only for best-effort enrichment (mitigation/effort/file:line), never as the source of truth for counts or provenance.
  - Self-contained HTML (`core/report/render-findings-html.js`, same offline-file discipline as `devteam report`) plus `--json`, schema-checked against `core/report/schemas/findings-report.schema.json`. The no-findings case renders an honest empty state, not a broken table.

  Honest scope note: file:line extraction is regex-based best-effort text parsing (`path/to/file.ext:NN` token matching), not a structured field on every source — security-review and peer-review blockers, in particular, only have a file:line when the reviewer happened to write one inline. Critic-challenge provenance is `model-asserted` for the claim content even when the hook mechanically forced its disposition to `unresolved` for missing evidence — this module doesn't split provenance within a single finding.
