### Added

- **Stage DAG wave execution (ADR-017, phase-32 item 32.6).** `full`-track runs paid 18 sequential stage slots even where two regions are independent. `core/pipeline/stages.js` gains a curated `dependsOn: string[]` field on exactly the two regions ADR-017 authorizes — `red-team` now depends on `build` instead of its declared-order predecessor `pre-review`, and each of `accessibility-audit` / `observability-gate` / `verification-beyond-tests` / `performance-budget` depends on `qa` — with a header comment on the STAGES table warning that any future region needs its own readFirst-vs-`dependsOn` curation pass, not a mechanical extension. **`red-team`'s `readFirst` drops `pipeline/pre-review.md` and `pipeline/security-review.md`** — a model-visible prompt change, not an incidental side effect of adding `dependsOn`: leaving them in would make `{pre-review ∥ red-team}` an unsafe pairing (see ADR-017's own design-conflict analysis).

  `core/orchestrator.js#_nextImpl`'s loop body is extracted into `evaluateStageInPipeline` (a pure per-stage readiness/action check) with zero behavior change — verified by the full pre-existing test suite before any wave code was added on top. The new `nextWave()` (exported alongside `next()`) is a thin wrapper: it runs the identical sequential scan for the first ready action, then — only when that action is a fresh/resuming dispatch and `autonomy.max_parallel_stages` (new config, default **2**, validated like `max_retries`) allows more — looks ahead for `dependsOn` stages whose named dependencies already hold PASS/WARN, regardless of declared order. A one-member result is byte-identical to `next()`.

  `core/scheduler.js` gains `waveMemberKey` (`(host, stage)` composite) so a future caller batching wave members through `mapByHostConcurrency` doesn't let `routing.host_concurrency` — designed to bound workstream fan-out *within* one stage — incorrectly throttle concurrency *across* stages that happen to share a host.

  `core/driver.js`'s main loop now calls `nextWave()` and, for a real 2+ member ready set, dispatches every member concurrently (`dispatchWaveMember`/`dispatchWave`, mirroring the pre-017 run-stage/continue-stage handling exactly, just returning a control signal instead of directly break/continue-ing the loop) via `Promise.all` — one member failing halts wave *advancement* (the driver won't form a new wave until every current member reaches a terminal state) without touching an already-passing sibling's gate. One monotonic-per-run `wave_id` is assigned per formed wave and stamped on every member's dispatch events; `state.iterations`/`--max-iterations` count one wave as one iteration. A `opts.next` single-action stub (the pre-existing test DI seam, used by ~120 call sites across the test suite) is automatically wrapped into a size-one wave when no `opts.nextWave` is given, so no existing test needed to change.

  `devteam performance critical-path` (`core/performance/critical-path.js`) gains a `waves` array and `wave_realized_savings_ms` (`sum(member durations) − max(member durations)`, grouped by `wave_id`) — additive to the existing sequential dispatch-wall-time accounting, not a correction to it.

  Docs: `docs/runbooks/autonomous-run.md` gains a "Stage DAG waves" section and a `wave-formed` entry in the non-halt events list; `docs/FEATURES.md` gains a matching bullet. `plans/phase-32-performance-parallelism.md`, `plans/README.md`, and `plans/prompts/roadmap-2026-prompts.md` updated so no document still shows 32.2/32.6 as open.

  Tests: `tests/dag-wave-execution.test.js` (27 cases) — curated `dependsOn`/readFirst trim; config validation and fallback; `waveMemberKey`; wave formation (`{pre-review, red-team}` and all four QA-sweep stages becoming ready together, `max_parallel_stages` capping and splitting, a size-one wave byte-identical to `next()`, a FAIL not removing a ready sibling); driver integration (concurrent dispatch writing both gates in one iteration, a shared monotonic `wave_id`, a size-one wave carrying no `wave_id` field at all, a FAIL not corrupting the passing sibling's gate, `verify-chain` passing on a waved run); legacy `opts.next` stub compatibility; critical-path realized-savings math and markdown rendering. `tests/compact-qa-fold.test.js`'s four hard-coded pre-29.4 stage snapshots updated to include the new `dependsOn` field — deliberately, since that's new authorized behavior this item adds, not drift the snapshot should catch.

  Honest scope note: only fresh/resuming dispatches (`run-stage`/`continue-stage`) are batched into a real concurrent wave. A ready set containing a `fix-and-retry` (or any other non-dispatch action) always collapses to a single-member wave and runs through the exact pre-017 code path unchanged — concurrent convergence/archiving bookkeeping for multiple *simultaneously failing* wave members was judged materially riskier than this item's wall-clock claim requires (that claim comes from concurrent fresh dispatch, not concurrent retry), and ADR-017 §6 itself only says a wave-aware `next()` "may" return more than one `fix-and-retry` action, not that it must.
