### Added

- **`loop` track: a 4-slot minimal-ceremony pipeline — phase-29 item 29.1.** New track `loop` (`STAGES_BY_TRACK.loop` in `core/pipeline/stages.js`): `requirements` (stage-01, one-screen brief) → `build` (stage-04, single workstream) → `qa` (stage-06) → `peer-review` (stage-05, single reviewer). Note the order — `qa` runs before `peer-review` on this track, the reverse of every other track; `verifyChain`'s nearest-earlier-gate predecessor rule already walks the track array in declared order rather than by numeric stage ID, so the tamper-evident chain still links correctly (new tests in `tests/chain.test.js` prove this explicitly). Build and peer-review each dispatch one config-overridable workstream (`pipeline.loop_build_role` in `.devteam/config.yml`, default `backend`) instead of the four-role matrix — `loopBuildRole()` in `core/pipeline/stages.js` is the single source of truth both `rolesForStage()` and `requiredApprovalsFor()` read, so the reviewed area always matches what build actually touched. Stage-01 renders a new one-screen template (`templates/loop-brief-template.md`: intent, AC-N list, affected files) on this track only, via a new `trackOverrides` mechanism on the stage definition (parallel to the existing `repairOverride`). `loop` has no design, no red-team, and no sign-off/deploy — `devteam run --track loop` ends at `peer-review`; promoting to a deploy-capable track is a re-run with `--until` on a bigger track or a `custom_stages` config, not a `loop` feature. `loop` is also added to `core/guards/stoplist.js`'s `STOPLIST_TRACKS` — the consequence ceiling applies to the lightest track exactly like the other lighter tracks. Docs: `docs/tracks.md` (new "The `loop` track" section + matrix row), `rules/pipeline-tracks.md`, and every other stage/track-count claim the consistency checker flagged (`docs/concepts.md`, `docs/FEATURES.md`, `docs/README.md`, `docs/comparative-analysis.md`, `docs/presentation-notes.md`, `docs/adr/006-track-inference-under-autonomy.md`, `docs/verification-beyond-tests.md`, `docs/user-guide.md`, `rules/gates-core.md`, `rules/orchestrator.md`, `roles/red-team.md`). Tests: `tests/tracks.test.js` (track shape + role/approval sizing, including the config override and its unrecognized-value fallback), `tests/pipeline-e2e.test.js` (a full stubbed `loop` run completes in exactly 4 dispatches, no merges, with an audit trail identical in shape to the other tracks), `tests/chain.test.js` (the inverted stage-06→stage-05 predecessor link stamps and verifies, and tamper detection still locates the break), `tests/orchestrator.test.js` (the track-based template override reaches the rendered prompt end-to-end via `runStage`, and repair intent still wins over the loop override), `tests/run.test.js` (the stoplist halts a `loop` run exactly like `quick`), `tests/config.test.js` (`loop_build_role` default and override), `tests/contract.test.js` (every `trackOverrides` template exists on disk). Honest scope note: track *selection* — `devteam assess` inferring `loop` from a change description — is out of scope for this item (phase-29 item 29.2); `loop` is opt-in via `--track loop` or `pipeline.default_track: loop` only.
