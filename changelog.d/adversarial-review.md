### Added

- **Adversarial reviewer/critic mode for stage-05 — Phase 31.3.** New `review.mode: "panel" | "adversarial"` config (default `panel`, byte-identical to today — no behavior change without opt-in). Adversarial mode replaces the four-area review matrix with exactly two sequential workstreams: a single **reviewer** covers every applicable area in one pass (`pipeline/code-review/by-reviewer.md`), then a **critic** — new role brief `roles/critic.md` — is dispatched only after the reviewer's gate lands and attacks the review itself: missed findings, unsupported approvals, and an explicit "what would make this approval wrong?" for every approved area, with file:line evidence required for every challenge. `core/hooks/approval-derivation.js` reuses `parseReviewFile()` verbatim for `by-reviewer.md` (rolled into one combined `stage-05.reviewer.json` gate rather than four per-area gates) and adds a parallel `parseCriticFile()`/`applyCriticVerdict()` for `by-critic.md`'s `challenges[]`/`challenges_resolved`; a challenge missing parseable `FILE:<path>:<line>` evidence is mechanically forced to `unresolved` regardless of what the critic wrote. `mergeWorkstreamGates()` surfaces `challenges`/`challenges_resolved` on the merged `stage-05.json`; the merge PASSes only when the reviewer gate PASSes AND `challenges_resolved` is true — an unresolved challenge blocks the stage regardless of the reviewer's own approval.

  Routing: `core/config.js#resolveHost` defaults the critic to a different host than the reviewer when ≥2 hosts are configured anywhere in `routing` (collusion counter-measure — 2026 evidence cited in `plans/phase-31-verification-depth.md` §31.3 found review panels underperform and are collusion-prone relative to an adversarial reviewer/critic pair); `routing.roles.critic` overrides. Mutually exclusive with `routing.review_fanout` per run — adversarial mode wins if both are configured.

  Scheduling: `core/scheduler.js`'s `mapByHostConcurrency` has no dependency-ordering primitive (only per-host concurrency caps — confirmed via `[verify-first]`, ADR-015 flags DAG-wave ordering as unimplemented future work). Implemented per the plan's documented fallback — "two orchestrator steps": `core/orchestrator.js#dispatchWavesFor` splits adversarial stage-05 into a reviewer wave and a critic wave inside `runStageHeadless`, awaiting the reviewer wave's `mapByHostConcurrency` call before starting the critic's, so the critic always sees the reviewer's completed file. Every other stage (and panel-mode stage-05) gets a single wave — identical to pre-31.3 behavior. `next()`/`_nextImpl`'s completed/remaining bookkeeping for stage-05 now resolves the actually-dispatched role list via `rolesForStage(stageDef, track, config)` instead of the static 4-area list, so adversarial mode's `stage-05.reviewer.json`/`stage-05.critic.json` gates are recognized and the stage can reach `merge` — panel and nano tracks are unaffected (`rolesForStage` returns the same role list they already used).

  Tests: `tests/adversarial-review.test.js` — `rolesForStage`/`computeDispatchPlan` return `["reviewer","critic"]` only under `review.mode: adversarial`; `dispatchWavesFor` splits into two waves for adversarial stage-05 and returns a single unchanged wave for every other stage/mode; `parseCriticFile`/`applyCriticVerdict` (unresolved challenge → FAIL, resolved → PASS, missing evidence forced unresolved); `applyAdversarialReviewerFile` (approved areas → PASS, a changes-requested area → FAIL); `resolveHost` cross-host default for critic (1 configured host → no diversity; ≥2 → different host; explicit `routing.roles.critic` always wins); merged-gate stubbed flow (reviewer PASS + critic unresolved → merged FAIL; reviewer PASS + critic resolved → merged PASS) via seeded gates, mirroring `tests/pipeline-e2e.test.js`'s style. Full existing suite (`tests/fanout.test.js`, `tests/approval-derivation.test.js`, `tests/next.test.js`, `tests/pipeline-e2e.test.js`, `tests/schemas.test.js`) re-run unchanged to confirm panel mode stays byte-identical.

  Honest scope note: the critic's `disposition` field is written by the critic itself (there is no second-round "someone else confirms the fix" step in this phase) — a critic marking its own challenge `RESOLVED` on a re-run is trusted, the same trust model panel-mode reviewers already operate under for `REVIEW: APPROVED`. Combining `review.mode: adversarial` with `routing.review_fanout` is not supported (adversarial mode silently wins); a future phase could define what N-host adversarial fanout even means. `core/orchestrator.js`'s experimental Omnigent-director path was not extended for adversarial stage-05 — it already requires every workstream to route to the `omnigent` host, which is orthogonal to this item's host-diversity goal.
