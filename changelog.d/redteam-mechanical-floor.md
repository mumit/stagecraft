### Added

- **Mechanical red-team floor for stage-04c — Phase 31.2.** Red-team's adversarial pass stayed 100% model self-report: a gate claiming `findings_count: 0` was believed, in the one stage whose job is distrust. `core/verify/redteam-floor.js` adds four orchestrator-run checks post-dispatch: (a) `npm audit --json` (or `pipeline.verify.dependency_audit_command` override; explicit `null` disables) — a network-unavailable audit records `skipped: "offline"`, never a pass; (b) the existing `core/hooks/secret-scan.js` reused as a library over the changed-file set (`pipeline/changed-files.txt`, falling back to `git diff --name-only HEAD`); (c) semgrep, only when the project already has a semgrep config file **and** the binary is already on PATH — devteam never installs either; (d) a lockfile delta (new/removed top-level `package-lock.json` entries) against the previous stage-04c attempt, read from `core/gates/archive.js`'s per-attempt archives, so a first attempt records a baseline snapshot rather than a false empty diff. `core/verify/stamp.js#stampStage04c` merges these into the gate: `findings_count := max(model_reported, mechanical)`, `severity_breakdown` is raised per-band the same way, and any mechanical `high`/`critical` finding is appended to `must_address_before_peer_review` with `source: "mechanical"` — which pushes a blocker onto the gate, so `finalizeStamp`'s existing PASS/WARN→FAIL override fires exactly like every other stamped stage. Rather than re-implementing the `pipeline/context.md` blockers-injection, `core/gates/validator.js#injectRedTeamBlockers` is now exported and called directly from `stampStage04c` so a mechanically-forced FAIL surfaces to the next build re-run the same way a model-authored FAIL always has. `stage-04c` joins `STAMPABLE_STAGES` (`devteam verify stage-04c` now works) using the existing single-workstream dispatch path in `core/orchestrator.js` — no orchestrator wiring changes were needed there.

  Tests: `tests/verify-stamp-04c.test.js` — a seeded critical dependency vulnerability flips a model-PASS gate to FAIL; an offline dependency audit records `skipped: "offline"` and does not affect gate status; explicit-disable and non-Node-project skips are recorded with distinct reasons; missing semgrep config skips honestly; model `findings_count: 0` + 2 mechanical (medium-severity) secret-scan findings merges to `2` without forcing FAIL (severity floor, not count floor, drives the forced-blocker path); a model-reported count already above the mechanical count is never lowered; missing/first-attempt lockfile-diff cases; every tool's stamp record carries `{ran, skipped, reason, findings}`.

  Honest scope note: **[verify-first] finding** — the plan item's claim that a "polyglot equivalent" of `npm audit` already exists via the Phase 19/PR #264 suite-detection does not hold; that work (`core/verify/runner.js`) discovers *test* commands (Node/pytest/go test) only, with no dependency-audit/SCA analog for non-Node ecosystems (no pip-audit/govulncheck wiring). The dependency-audit check therefore only runs for Node projects (`package.json` present) or via the `dependency_audit_command` override; other project types record an explicit skip rather than guessing at unvetted tooling. The lockfile-delta check only understands `package-lock.json` (npm lockfileVersion 1–3), matching the same Node-first scope. Semgrep is scoped to the changed-file set (not a full-repo scan) to keep the mechanical floor time-boxed. The lockfile-delta's "previous attempt" lookup reuses `core/gates/archive.js`, which only archives a stage-04c attempt when it was `FAIL` — a `PASS` attempt is never archived, so a diff run after an unbroken PASS streak has no prior snapshot to compare against and records a fresh baseline rather than a true delta. A dedicated snapshot store (independent of FAIL-only archiving) would close this gap but is out of scope for this item.
