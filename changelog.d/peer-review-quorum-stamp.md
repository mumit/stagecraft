### Added

- **Stage-05 (peer-review) quorum re-derivation — Phase 31.5.** Approval state was only kept honest by the claude-code PostToolUse hook (`core/hooks/approval-derivation.js`); on every other host — and any claude-code save that happens outside the hook, which is why `devteam derive-approvals` exists — a workstream gate could claim `PASS` off a status that was never actually derived from `pipeline/code-review/by-*.md`. `core/verify/stamp.js#stampStage05Merged` closes that gap: after stage-05 merges, the orchestrator re-derives approval state itself by calling the hook's own `parseReviewFile()` directly (never reimplementing the `REVIEW:`/`CHANGES REQUESTED` grammar) over every `by-*.md` file, on every host, unconditionally. A panel-mode workstream gate (`backend`/`frontend`/`platform`/`qa`) claiming `PASS` whose review file says `CHANGES REQUESTED` — or has no parseable verdict for that area at all — flips the merged stage-05 gate to `FAIL`, with a `{field: "approval_state", workstream, gate_said, file_said}` record on `_orchestrator_stamped.fields` and a matching blocker. `stage-05` joins `STAMPABLE_MERGE_STAGES` alongside `stage-04`, wired through the existing merge-time stamping call site in `core/driver.js` (no new call sites needed).

  Tests: `tests/verify-stamp.test.js` — a seeded mismatch (gate says `APPROVED`, review file says `CHANGES REQUESTED`) flips the merged gate to FAIL with the field-level record; agreeing states leave the merge untouched (no fields recorded, no status override); a workstream claiming `PASS` with no matching review-file section at all is recorded as its own `NO_PARSEABLE_VERDICT` mismatch class; adversarial mode's `reviewer`/`critic` workstreams are left untouched. Also updated `tests/verify-stamp.test.js`'s pre-existing "stampMerged rejects a stage with no merged stamping defined" test, which used `stage-05` as its not-yet-stampable example — swapped to `stage-06`, which still has no merged stamper.

  Honest scope note: scoped to panel mode's per-area workstreams only. Adversarial mode's (31.3) `reviewer`/`critic` workstreams aren't area-named — `by-reviewer.md` rolls every area into one combined gate and `by-critic.md` uses a different (challenge) grammar entirely — so re-deriving them against a per-area map isn't a valid comparison; they're left to their own existing verification path (evidence-required challenge disposition). This re-derivation also doesn't recompute *how many* distinct reviewers approved an area (the `required_approvals` count) — only whether any review file for a `PASS`-claiming area contradicts or is silent on that claim. Re-verifying quorum counts independently would be a natural follow-up but is out of scope for this item.
