### Added

- **Attestation export: gate chain → in-toto-Statement-shaped signed evidence bundle — phase-34 item 34.2 (`docs/evidence.md` "Attestation export").** `devteam evidence export --attestation [--out <file>] [--sign] [--allow-unverified] [--track <t>]` productizes the existing Phase 16–18 evidence subsystem and the C6/ADR-011 gate chain into a full per-stage-fidelity proof of ONE run/commit — the opposite shape from `evidence export`'s privacy-preserving cross-run aggregate, and never mixed with it. `core/evidence/attestation.js` runs `verifyChain` first and refuses to attest a broken chain unless `--allow-unverified`, which proceeds anyway and stamps `predicate.unverified: true` with the full `chain_verification` detail rather than hiding the problem. `predicate.stages` carries one entry per stage gate: per-field provenance distinguishing model-asserted values from orchestrator-observed/stamped ones (reusing the `_orchestrator_observed`/`model_requested` convention `core/orchestrator.js` already established), the C4 reproducibility fingerprint via `core/reproducibility.js`'s existing `reproducibilityFingerprint` (not reimplemented), `prompt_pack_version` (33.3) when present, this gate's chain-hash linkage plus HMAC presence (never the raw HMAC value), and C6/Phase-2 `resolved_by` authority-resolution provenance when applicable. `predicate.resolutions` lists every ADR-012 accepted fix/retry resolution from the run log as its own entry. `subject` is the commit(s) the run produced — `auto-commit` run-log events when present, falling back to the current git `HEAD` for the common manual-commit workflow.
  - **Schema (`core/evidence/schemas/attestation.schema.json`).** A checked-in, strict, closed JSON Schema mirrors `validateAttestation`'s hand-rolled reader (same house convention as `evidence-export.schema.json`/`bundle.js` — no ajv dependency added); every emitted bundle is validated against it before being written, and `payload_sha256` (canonical-JSON digest, the same technique `core/gates/chain.js`/`core/evidence/bundle.js` already use) lets `devteam evidence verify-attestation <bundle>` offline re-check both schema conformance and tamper evidence without touching the live pipeline.
  - **`--sign`.** Shells to `cosign sign-blob --output-signature <file>.sig <file>` only when `cosign` is found on PATH (probed the same way `core/verify/redteam-floor.js` probes for `semgrep`); a missing or failing `cosign` exits non-zero with a clear error, but the attestation bundle itself is still written first — signing is a best-effort layer on top of an already-valid, already-useful bundle. Stagecraft never bundles or manages signing keys.
  - Tests (`tests/attestation.test.js`, 18 cases): schema-valid bundle from a fixture pipeline; per-field provenance and C4 fields on stage entries; orchestrator-observed vs model-asserted divergence; ADR-012 accepted resolutions appear as their own entries; broken-chain refusal and the `--allow-unverified` escape hatch; no-producible-commit refusal; write/read round-trip and tamper detection via the payload digest; full CLI coverage of `export --attestation` and `verify-attestation`; `--sign` against a stubbed `cosign` on PATH, a cosign failure, and cosign's absence.
  - Honest scope note: "in-toto-Statement-shaped", not in-toto/SLSA-compliant — `predicateType` is Stagecraft-namespaced (`urn:stagecraft:attestation:1.0`), not a registered SLSA/in-toto predicate, and `payload_sha256` is a Stagecraft-local tamper check, not a DSSE envelope. `--sign` produces a detached `cosign` signature file alongside the bundle rather than an embedded DSSE signature. Signing-key management (cosign keyless/KMS/Fulcio setup) is entirely the operator's responsibility, per the phase-34 plan's explicit scope boundary. Subject-commit resolution requires a git repository with at least one commit; a project with no commits and no `--auto-commit` history cannot be attested yet.
