### Added

- **`devteam review-pr <number|url>` — phase-35 item 35.2 (`plans/phase-35-existing-codebase-mode.md`).** Review an inbound GitHub PR with the existing reviewer/critic machinery instead of hand-assembling a brief. Materializes the PR via `gh pr view`/`gh pr diff` into `pipeline/review-input/` (`pr.md` — title/body as the stated intent; `diff.patch` — the unified diff; `changed-files.md` — the changed-file list), then dispatches `peer-review` (stage-05) against it on a new `review-pr` track: a single "reviewer" workstream in panel mode (`PEER_REVIEW_SIZING["review-pr"]`, sized like `nano` rather than `review-only`'s four-area matrix — a PR is already one bounded, diffed unit of change), reviewer-then-critic when `review.mode: adversarial` (31.3) — that override is config-driven exactly as it is everywhere else, no new flag needed. Output is a normal stage-05 gate (`pipeline/gates/stage-05.json`, or the merged adversarial gate) plus `pipeline/code-review/by-*.md`, dispatched through the unmodified `runStage`/`runStageHeadless`/`mergeWorkstreamGates` path — 35.1's soft-readFirst already made `peer-review` tolerant of a repo with no `pipeline/brief.md`/`design-spec.md`, and three new optional `readFirst` entries (`pipeline/review-input/{pr.md,diff.patch,changed-files.md}`) were added to both the panel and adversarial-override shapes so the materialized PR is only ever mentioned in the prompt when it actually exists.

  `gh` auth/error handling is reused verbatim from `scripts/pr-publish.js` (the only existing place that shells to `gh`) — `gh`/`ensureGh` are now exported from there rather than duplicating a second pattern.

  **Publishing is opt-in and gated.** Default is local-only: findings land on disk, nothing is sent anywhere. `--post` publishes the combined `by-reviewer.md`(`+by-critic.md`) content as a `gh pr review --comment` PR review comment: it prints the exact payload (to stderr, so `--post --json` still emits one clean JSON object on stdout), then requires interactive confirmation — auto-confirmed with `--yes`, required in a non-interactive context (no TTY) since there's no one to prompt. Refuses outright, before ever building a payload, when the dispatch was partial (a workstream timed out, exited non-zero, wrote no gate, or the adversarial merge failed) — a FAIL/ESCALATE gate that *completed* is still postable (that's the point — post the findings), only an *incomplete* dispatch is refused.

  Tests (`tests/review-pr.test.js`): a scripted `gh` stub + a `DEVTEAM_HEADLESS_COMMAND` writer script (mirrors `tests/replay.test.js`'s pattern) drive a full `devteam review-pr` CLI invocation end to end — materialization content, panel-mode single-workstream gate, a bare-number vs. full-URL positional argument, adversarial mode's reviewer+critic merge, `--post` refusing (and posting nothing) in a non-interactive context without `--yes`, `--post --yes` actually calling `gh pr review` with the expected body, missing `gh` giving an actionable error instead of a stack trace, and a partial dispatch (`DEVTEAM_HEADLESS_COMMAND=true`, no gate written) refusing `--post` even with `--yes`.

  Docs: `docs/tracks.md` gained a `## The review-pr track` section and its generated stage matrix regenerated (`scripts/generate-tracks-matrix.js` now marks review-pr's peer-review `✓ˢ`, same annotation as nano's single-reviewer scoping); `docs/concepts.md`, `docs/FEATURES.md`, `rules/pipeline-tracks.md`, `rules/gates-core.md` updated from eight to nine tracks; `docs/reference/cli.md` regenerated (`npm run docs:generate`) to include the new command.

  Honest scope note: `core/gates/schemas/gate.schema.json`'s `track` enum gained `"review-pr"` — it was already missing `"loop"` (pre-existing drift flagged, not fixed, by the 35.1 changelog; still not fixed here). `rules/pipeline-tracks.md`'s per-track approvals table predates `review-only` and still doesn't list either `review-only` or `review-pr` — flagged inline with a pointer to `docs/tracks.md` rather than expanded, to avoid widening this item's diff into an unrelated table rewrite. `review-pr`'s single "reviewer" workstream reuses the exact role name the 31.3 adversarial override already treats specially (`by-reviewer.md` → `applyAdversarialReviewerFile`) purely as a filename-matching side effect of `core/adapters/headless.js`'s post-dispatch approval-derivation fallback — harmless (the model's own direct gate write to `pipeline/gates/stage-05.json`, per every stage's "## Gate to write" contract, is what the orchestrator actually reads) but it does mean a redundant `stage-05.reviewer.json` gets written alongside the real gate on panel-mode runs, exactly as nano's `backend`-named single workstream already leaves behind an unused `stage-05.backend.json` today. Not fixed here — pre-existing characteristic of the single-workstream shape, not something 35.2 introduces.
