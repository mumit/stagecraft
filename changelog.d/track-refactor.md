### Added

- **`refactor` track — behavior-preservation for structural changes (phase-35 item 35.5, `plans/phase-35-existing-codebase-mode.md`).** `devteam run --track refactor` dispatches the same 3-stage shape as `nano` (`build` → `peer-review` → `qa`, single-reviewer sizing) but with a different bar: no new acceptance criteria, the existing test suite must pass **unchanged**, and a surviving mutant is treated as evidence the refactor didn't preserve behavior.
  - **Build (stage-04)** gets a `trackOverrides.refactor` on `core/pipeline/stages.js`: the objective and template (`templates/characterization-template.md`) swap to a CHARACTERIZATION brief — document current behavior (inputs/outputs, edge cases, error handling, existing test coverage) *before* touching structure. Gate shape is unchanged from `nano`.
  - **QA (stage-06)** gets a matching `trackOverrides.refactor`: `all_acceptance_criteria_met` and `criterion_to_test_mapping_is_one_to_one` are seeded `null` (no brief.md exists on this track, same as `nano` — `core/verify/stamp.js#checkAcceptanceCriteria` already treats a missing brief as not-applicable and leaves the field untouched, so `null` is the honest initial value rather than `false`). `core/gates/schemas/stage-06.schema.json` widens both fields' type to `["boolean", "null"]`.
  - **The 31.4 mutation smoke gate defaults to *enabled*** on the `refactor` track only (`core/verify/mutation.js#defaultMutationEnabledFor`) — every other track keeps its pre-35.5 opt-in-off default. An explicit `pipeline.verify.mutation.enabled` in config always wins over the track default, in either direction. `core/verify/stamp.js#stampStage06` now threads `gate.track` into `runMutationGate`.
  - `PEER_REVIEW_SIZING.refactor` mirrors `nano`'s (single reviewer, 1 approval) — without this entry the track would silently fall back to the full 4-area matrix. `core/gates/schemas/gate.schema.json`'s `track` enum gained `"refactor"`.

  Tests: `tests/refactor-track.test.js` — track/stage-list/sizing contract identical to `nano` except the two documented differences; `build`/`qa` descriptors diverge from `nano` only on the objective/template/gate fields called out above; `resolveMutationConfig` defaults on for `refactor` and off for every other track (explicit config always wins); `stampStage06` integration proving the mutation gate actually runs by default on `refactor` and stays skipped on `nano` with the same unconfigured verify block; a behavior-changing edit (existing test suite failing) FAILs stage-06 on `refactor` via the ordinary test-command blocker — no new mechanism needed, it's the same check every other track already has; `--track refactor` walks `build → peer-review → qa` to `pipeline-complete` on a fixture with a complete, correctly-null audit trail.

  Honest scope note: the plan's "AC-mapping gate fields null-permitted as in 35.1" language describes a JSON-Schema `if/then` conditional keyed on `track`; this codebase's schemas are not ajv-validated at runtime (`tests/schemas.test.js`'s own header notes this — "avoids adding ajv as a dep"), so the schema change here is a type-widening (`["boolean", "null"]`), not an enforced per-track conditional — the actual per-track behavior lives in the `trackOverrides.refactor` gate skeleton and in `checkAcceptanceCriteria`'s pre-existing not-applicable handling. "The existing suite must pass unchanged" is enforced exactly as far as every other track already enforces "tests must pass" (the stage-06 test-command blocker) — this item does not add a mechanical check that test *files themselves* were left untouched during the refactor; that would be a further-reaching, unrequested mechanism.
