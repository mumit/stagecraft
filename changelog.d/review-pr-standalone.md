### Added

- **`devteam review-pr <number|url>` works with no checkout and no initialised project — phase-36 item 36.5 (`plans/phase-36-external-review-mode.md`).** Running from an already-initialised project (`.devteam/config.yml` present in `--cwd`) is byte-identical to before. Otherwise, `review-pr` now materializes the PR into a 36.3 review workspace (`core/review-workspace.js`) instead of the invoking directory: `gh pr view`/`gh pr diff` are fetched once, then written into `<workspace>/pipeline/review-input/` and dispatched exactly as the in-place path does, with `pipeline/gates/stage-05*.json` and `pipeline/code-review/by-*.md` landing under the workspace. The workspace is derived from the PR's own URL (`core/review-workspace.js#slugForIdentity`/`resolveWorkspacePathForIdentity`, new — `slugForSubject`'s `path.resolve()` would otherwise resolve a non-path identity against the invoking cwd, making the slug vary by invocation directory instead of by PR), so repeat reviews of the same PR reuse the same workspace regardless of where the command is run from. `--workspace <path>` overrides the derived path, mirroring `devteam review`.

  **No clone, ever, in this path.** The diff *is* the subject — `core/review-workspace.js#createReviewWorkspace()`/`writeSubjectManifest()` now accept `subjectPath: null` (required as an explicit key, not merely omitted, so a caller can't silently forget it) plus directly-supplied `remote`/`commitSha`/`pr` fields instead of shelling `git` against a path that doesn't exist; `subject.json` records `subject_path: null` and a `pr: {number, url, title}` block in that case. Dispatch sets `ctx.externalReviewMode: true` and a new `ctx.noCodeRoot: true` (threaded through `core/orchestrator.js#runStage()` exactly like 36.3's `processCwd`/`externalReviewMode` — unset on every other caller, so byte-identical there).

  **Fixed a real gap this surfaced in `hosts/acp/adapter.js`.** `hosts/acp/permissions.js#findWriteViolation` already special-cased a falsy `codeRoot` for this exact scenario (comment naming 36.5 was already in the file from an earlier item), but `adapter.js`'s own `codeRoot: processCwd` — where `processCwd = ctx.processCwd || ctx.cwd` — never actually produced a falsy `codeRoot`: with `ctx.processCwd` unset, `codeRoot` silently became `ctx.cwd` itself (i.e. `codeRoot === stateRoot`), which `findWriteViolation` reads as "every write target is inside the subject" and denies outright. `ctx.noCodeRoot` is the fix: `codeRoot` is `null` only when explicitly opted into, leaving the existing fail-closed default (deny when `processCwd` is merely omitted, protecting against a review-mode dispatch that forgot to set up a real code/state split) completely intact for every other caller.

  **Publishing safety is untouched.** `--post` stays opt-in, the confirmation still throws (not a silent no-op) and actually stops the command, non-interactive still requires `--yes`, and a partial/incomplete dispatch still refuses to post even with `--yes` — re-verified with a parallel copy of every 35.2 publishing-safety test run against the new no-project-directory path, plus the original in-place suite re-run unmodified.

  Tests: `tests/host-acp.test.js` — an end-to-end `adapter.invoke()` case proving a write under `ctx.cwd` matching `allowedWrites` is allowed with `ctx.noCodeRoot: true` and no `ctx.processCwd` (fails without the `adapter.js` fix), plus a sibling case proving the same paths are still denied when `ctx.noCodeRoot` is merely omitted (guards against re-loosening the pre-existing fail-closed test). `tests/review-workspace.test.js` — `slugForIdentity`/`resolveWorkspacePathForIdentity` stability and cwd-independence, `createReviewWorkspace`/`writeSubjectManifest` with `subjectPath: null`, the required-key throw, and `runStage()` threading `ctx.noCodeRoot`. `tests/review-pr.test.js` — a scripted `gh` stub drives `devteam review-pr <url> --json` from a plain tmpdir with no `.devteam/` and `STAGECRAFT_REVIEWS_DIR` pinned to a fresh tmpdir: asserts the workspace path reported in `--json`, that nothing lands under the invoking cwd, that `subject.json` records the PR's identity, that a repeat run reuses the same workspace, and re-runs the non-interactive-refusal / `--post --yes` / partial-review-never-posts cases from 35.2 against this path. The full original `tests/review-pr.test.js` suite (in-place mode) passes unmodified.

  Honest scope note: no `--host`/adversarial-mode support in workspace mode — the workspace's generated `.devteam/config.yml` pins `routing.default_host: claude-code` and sets no `review.mode`, so a bare-PR review from an uninitialised directory always runs single-reviewer panel mode; adversarial mode and a different host still require an initialised project (`--cwd` pointed at one) until a future item exposes equivalent flags, mirroring `devteam review`'s `--host`. A bare PR *number* (as opposed to a full URL) still requires being run inside an actual checkout of the repo — `gh` infers the target repo from the invoking directory's git remote, which a URL doesn't need; this is a pre-existing `gh` behavior, not something this item's code decides, and isn't newly broken by it. Also found, and left as documentation only: `core/cli/commands/review-pr.js`'s pre-36.5 precondition check (`.devteam/config.yml` absent) never actually refused — it printed a cosmetic stderr warning and then dispatched into the invoking `cwd` regardless (no downstream guard existed either, confirmed by reading `core/config.js#loadConfig`'s silent-defaults fallback and `core/orchestrator.js#runStageHeadless`). The in-place code path is left exactly as it was; the new workspace routing described above is this item's actual fix for that gap, not a hardening of the old warning.
