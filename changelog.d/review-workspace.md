### Added

- **Review workspace + dispatch plumbing — phase-36 item 36.3 (`plans/phase-36-external-review-mode.md`).** `core/review-workspace.js` creates `~/.stagecraft/reviews/<slug>/` (`--workspace <path>` overrides), where `<slug>` is the subject's basename slugified plus a short stable hash of its absolute path (collision-safe across two checkouts sharing a basename; stable across repeat reviews of the same path). The workspace mirrors the parts of `devteam init` a review needs — `pipeline/gates/`, a minimal `.devteam/config.yml` pinning `routing.default_host`/`pipeline.default_track`, and the given host adapter's own `install()` for role prompts/rules/templates/skills (ACP's `.acp/stagecraft/{roles,skills}` per `hosts/acp/capabilities.json`) — reusing the existing adapter contract rather than hand-rolling a second install path. `.devteam/patterns`, `corpus`, and `evals` are deliberately not pre-created: every consumer already `mkdirSync(..., {recursive:true})`s on first write, same as a freshly-`init`'d project.

  `createReviewWorkspace()` also writes `subject.json`, recording the subject's absolute path, its `git remote get-url origin` (null if none/not a git repo), and the commit SHA at workspace-creation time — so a future attestation pass can name **what was reviewed**, not what was produced (34.2's `resolveSubjectCommits()` reads `ctx.cwd`'s own git history, which is empty for a review workspace; wiring that read is left to a later item, not this one — see honest scope note).

  **Orchestrator plumbing.** `core/orchestrator.js#runStage()` now threads `opts.processCwd`/`opts.externalReviewMode` onto `ctx`, the same passthrough `opts.scope` already gets (phase-35 item 35.1); `core/driver.js#run()`'s single `_runStageHeadless()` call site threads them the same way. Both default to `null`/`false` when absent, so every existing caller is byte-identical. This is the wiring `hosts/acp/adapter.js` and `core/adapters/render-helpers.js#resolveFrameworkPath` (36.1/36.2) were already waiting on — `ctx.externalReviewMode` was previously set by no orchestrator path at all.

  New env var `STAGECRAFT_REVIEWS_DIR` (default `~/.stagecraft/reviews/`), same precedent as `STAGECRAFT_ORG_MEMORY_DIR` (`core/memory/index.js`) — see `docs/reference/environment-variables.md`.

  **The test that matters** (`tests/review-workspace.test.js`): a real dispatch through `hosts/acp`'s adapter (driven by the existing `tests/fixtures/acp-stub-agent.js` scripted agent — no network, no real model) against a `createReviewWorkspace()`-built workspace and a genuinely separate fixture subject repo, with `ctx.processCwd` = subject and `ctx.cwd` = workspace. The subject tree (file list + content hash, `.gitignore`/`AGENTS.md` included) is snapshotted before and after and asserted completely unchanged — both immediately after the real dispatch and again after the rest of the `review-only` track completes. Also covers: gates/logs landing under the workspace (not the subject); `subject.json`'s path/remote/SHA fields, including the no-git-repo fallback; `runStage()`/`driver.run()` opts passthrough (present and byte-identical-when-absent); and `devteam verify-chain --cwd <workspace>` passing against the resulting chain.

  Honest scope note: this item wires the workspace and the ctx split; it does not yet flip `ctx.externalReviewMode` on for any real CLI command (that's item 36.4's `devteam review <path>`) or wire `subject.json` into `core/evidence/attestation.js`'s subject resolution (flagged above, left for a later item since 36.3's own acceptance criteria doesn't require it). `driver.js` currently has exactly one `_runStageHeadless()` call site, so the passthrough only needed one edit; if a future item adds a second dispatch path, thread the same two fields there.
